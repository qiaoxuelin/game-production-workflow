# Visual Review (`Review`)

Review UI/2D evidence without changing project files or implementing repairs. Apply the core's existing independent-review, human-authority, experience-quality, gate, and return rules; do not duplicate, weaken, or grant them here.

## Inputs and observation

Require the exact maturity/product-quality claim, comparison basis, frozen Direction or Production design baseline, actual target-project artifact, applicable states/viewports, hard return conditions, and reviewer-contribution disclosure. Reuse the capability handshake for observation. When the claim needs runtime evidence, inspect the actual target result at intended size/device, representative content density, normal player pace, and applicable states; trace real input through authoritative state to visible feedback. If it cannot be observed, return the exact blocker and no conformance or quality result.

## Choose the comparison basis

- In `reference_replication`, use the named external reference/version and declared tolerances.
- In `original_design`, use the core-recorded frozen internal Production design for conformance and the declared player/platform/category quality bar for product quality. Category benchmarks and inspiration remain non-authoritative unless core explicitly adopts them into that baseline.
- In `original_design` before a trustworthy internal baseline is frozen, inspect Direction candidates against the supplied brief/category bar as recommendation only; otherwise inspect greybox/objective evidence. Report no design-conformance or product-quality passage and return the exact Design/core action. Never invent a reference or treat general polish as passage.

## Inspect four separate claims

1. **Objective validity:** applicable input, authoritative state, renderer, state/viewport coverage, source/import integrity, accessibility/performance, and provenance evidence are valid.
2. **Design conformance:** hierarchy, identity, composition, components/states, shared-space contact, continuity, source separation, focus/navigation, timing/interruption, failure/recovery, feedback, content extremes, and tolerances conform to the frozen baseline.
3. **Product quality:** readability, affordance, attention, interaction-to-visual causality, craft, coherence, and feedback meet the declared player/platform/quality comparison basis.
4. **Integrated acceptance:** the visual result fits the surrounding gameplay and scoped experience. Echo `Integrated acceptance` only when the input names a core-recorded acceptance; otherwise report readiness or a recommendation, never grant that maturity.

Passing one claim never implies another. Inspect only what the evidence supports and retain passing parts when returning a narrower failure.

## Authority and result

Disclose whether the reviewer materially contributed to the direction, source, or implementation. A creator self-check may support conformance but cannot satisfy an independent-review requirement. A gate-critical or repeatedly returned claim still needs the independent or human authority required by the core. The reviewer grants no gate, golden, producer, human, or lifecycle passage.

Return only `Pass`, `Pass with bounded non-blocking findings`, `Returned`, or `Blocked`:

- Use `Pass` only when every inspected claim meets its supplied criteria.
- Use `Pass with bounded non-blocking findings` only when findings do not invalidate the claim; name the retained evidence and bounded next owner.
- Use `Returned` when observable evidence fails a criterion; name the exact claim, retained passing parts, hard passage conditions, and next owner without repairing it.
- Use `Blocked` only when the claimed experience cannot be observed; name the observation blocker, fallback, and recovery path.

Return read-only `Changed paths: None`, the comparison basis, inspected claim, evidence and coverage, fidelity limits, reviewer contribution, unresolved risks, and one recommended next delta.
