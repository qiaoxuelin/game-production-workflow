# 3D art: models, materials, lighting, and scenes

Use only for the affected 3D asset or scene. Apply the selected art operation;
checks below are conditional on the asset and the frozen target, not a demand
for every project to add every pipeline feature.

## Design

Translate the selected direction into a buildable spatial brief: player camera,
view distance, world units, axes, scale, pivots/contact points, silhouette,
proportion, material response, light/exposure language, and gameplay readability.
Define editable model/scene or reproducible procedural source, engine destination,
export/import settings, texture/channel/color-space conventions, and project-
specific geometry, material, texture, lighting, and frame-cost budgets. Use the
actual target tier rather than universal polygon limits. Define modular seams,
sockets, collision/navigation responsibilities, or LOD behavior only when needed.
Rigging belongs only to deforming/animated assets; static props need no rig.

Use one scratch blockout or editor-scene feasibility check for the dominant
spatial/import risk. A concept render is direction evidence, not editable 3D
source or target-project proof. Return a production-design candidate to core;
core records the freeze before target-project Produce. Preserve an adopted
camera/style and describe only the requested delta.

## Produce

Consume the frozen brief; return missing product or art-direction decisions
instead of inventing them. Choose available DCC, engine-native, procedural, or
rights-cleared sources. If a tool is absent, inspect available alternatives;
use a declared greybox where permitted, or report the precise final-fidelity
blocker. Tool presence alone does not prove modeling/import/render capability.

1. Build one canonical editable source with recoverable exports. Check units,
   axes, transforms, pivots, bounds, normals/tangents, unintended holes or
   intersections, and silhouette/topology appropriate to the claimed use.
2. For textured assets, check UV distortion/seams, intended overlaps, texel
   density, channel packing, color space, compression, and material assignments.
   Untextured procedural materials need no invented UV requirement. Confirm
   shader support and material/light response in the target renderer.
3. Import deterministically and assemble one representative asset/scene in the
   actual project. Check scale/contact, camera framing, occlusion, modular joins,
   shadows/exposure, and the affected collision/navigation/attachment interfaces.
   Do not change gameplay physics or navigation authority to hide an art defect.
4. Run at the intended player camera and relevant distances/lighting states.
   Exercise affected gameplay interactions. Inspect source/import validity,
   runtime appearance, and measured frame/memory/draw or overdraw cost separately.
   Exercise LOD transitions only when present. Editor preview alone cannot prove
   player-camera appearance or target-device performance; disclose unavailable
   device measurements instead of substituting desktop numbers.
5. Keep bulk locked until representative assembly and runtime proof pass.
   Changes to shared scale, material masters, rigs, or lighting invalidate their
   declared dependents. Use the common Produce repair-and-return boundary.

## Review

Inspect editable source/import evidence and the actual engine result against
the frozen camera, spatial, craft, and performance criteria. Distinguish an
attractive offline render from runtime conformance, and static inspection from
measured performance. Reject broken contact, unintended intersections, bad
normal/material response, unreadable silhouette, or unverified dependent assets
when they invalidate the inspected claim. If necessary runtime observation is
unavailable, return that blocker and no runtime quality result. Do not repair
files or grant core acceptance. Animation evidence follows animation-vfx.md
only when motion is part of the claim.
