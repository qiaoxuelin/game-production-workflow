# Game and content design

Use this reference for gameplay, systems, levels, difficulty, balance, economy,
progression, content, or narrative work. Invoke only the affected disciplines;
one accountable owner may cover several adjacent concerns.

## Define the player contract

Freeze the player goal, meaningful decisions, information available before the
decision, action/feedback loop, success/failure/recovery, pacing, protected
rules, edge states, and target experience. For reference replication, derive
these from observed behavior and mark unknowns. For original design, explain
why the proposed rules serve the player and product goals rather than filling
gaps with familiar genre defaults.

Use the narrowest truthful maturity:

1. **Hypothesis:** a mechanic, level, economy, or content direction to test.
2. **Frozen design:** complete rules, values, state/coverage contract, rejection
   conditions, and implementation handoff for the scoped slice.
3. **Representative proof:** a real playable slice demonstrates the dominant
   feasibility, clarity, difficulty, and experience risks.
4. **Batch/integrated acceptance:** the scoped population and progression pass
   coverage, regression, and producer review.

## Gameplay and systems

Specify the core decision, causal response, state transitions, failure and
recovery, resource ownership, interruption, exploit/soft-lock boundaries, and
how the player learns the rule. Reject features that add presentation or a new
object without adding a meaningful player decision or perceptible consequence.

## Levels and difficulty

For each representative level or group, define its job in the learning curve:
introduce, contrast, combine, pressure, exam, payoff, or relief. State the
dominant difficulty driver, intended route or solution space, readable setup,
stability/feasibility constraints, target action budget, fail cause, and what
new skill the player demonstrates.

Design topology and interaction roles before coordinates. Use static schema,
support/route/coverage checks, or a disposable feasibility fixture before
runtime tuning. A spreadsheet that renders correctly is not proof that the
level is playable, readable, fair, or enjoyable. Prove a representative level
before producing a chapter or batch, and preserve passing lessons/results when
a later level returns.

## Balance, economy, and progression

Define goals and variables before selecting values. Map sources, sinks,
conversion, caps, pacing, scarcity, failure recovery, segmentation if relevant,
and the expected player path over time. Check conservation, boundary cases,
dominant strategies, grind/pay pressure, exploit loops, sensitivity to key
values, and save/version behavior with the cheapest suitable model or
simulation. Label internal test constants and unavailable offers clearly; they
do not constitute a commercial economy.

## Content and narrative

Define the reusable content grammar, prerequisites, variation dimensions,
pacing, repetition limits, state continuity, localization/accessibility needs,
and downstream asset/logic dependencies. Narrative must change or clarify the
player experience through authored states and consequences; text volume alone
is not narrative depth.

## Return and replan

Return the design before bulk work when the player decision is unclear, a new
item is only a reskin, difficulty is only larger numbers, coordinates conceal a
topology or capability problem, an economy lacks a source/sink and sensitivity
model, content variants repeat the same experience, or required states/routes
are missing.

If two bounded proofs fail the same causal criterion without new evidence,
stop tuning. Classify whether the design topology, production sequence,
enabling capability, technical model, or acceptance method is wrong; keep
passing sub-results and choose one new route before implementation resumes.

Keep evidence lean: the existing task or one design baseline, the cheapest
coverage check, one representative playable proof, and one consolidated
design-owner verdict normally suffice before bulk unlock.
